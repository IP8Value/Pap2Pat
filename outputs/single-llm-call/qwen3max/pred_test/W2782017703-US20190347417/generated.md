# DESCRIPTION

## BACKGROUND

Modern system-on-chips (SoCs) are complex integrated circuits that typically incorporate tens of intellectual property (IP) cores—both digital and analog—to perform a wide array of functions. These IP cores represent pre-designed, reusable blocks of logic or circuitry that implement specific functionalities such as encryption, signal processing, memory control, or communication protocols. To reduce research and development costs and accelerate time-to-market, SoC design houses frequently procure the majority of these IP cores from third-party (3P) vendors rather than developing them in-house. This widespread reliance on externally sourced IP introduces significant security concerns, particularly regarding the trustworthiness of these third-party IP (3PIP) cores. Specifically, untrusted 3PIP vendors may intentionally embed malicious hardware modifications known as hardware Trojans into their delivered IP cores. Such Trojans can create covert backdoors that enable adversaries to exfiltrate sensitive data, disrupt normal operation through denial-of-service attacks, or degrade system reliability, thereby compromising the integrity and confidentiality of the entire SoC.

The detection of hardware Trojans in 3PIP cores presents a formidable challenge in the semiconductor industry. Unlike traditional functional bugs, Trojans are deliberately designed to remain dormant during normal operation and activate only under rare or specific conditions, making them extremely difficult to uncover through conventional verification and testing methodologies. A fundamental obstacle is the absence of a trusted “golden” reference model against which a suspect IP core can be compared. In theory, activating a Trojan and observing its effects would confirm its presence, but without prior knowledge of the Trojan’s structure, location, size, or triggering mechanism, this approach is impractical. Moreover, industrial-scale IP cores often consist of thousands or even millions of lines of register transfer level (RTL) code written in hardware description languages (HDLs) such as Verilog or VHDL. Identifying a few malicious lines of code embedded within this vast codebase is akin to finding a needle in a haystack.

To address this threat, numerous Trojan detection techniques have been proposed in the literature, broadly categorized into structural analysis, functional analysis, symbolic algebra, formal methods, and information flow tracking (IFT). Structural analysis approaches employ statistical or heuristic metrics—such as low signal activation probability or unused circuit identification (UCI)—to flag suspicious circuit elements that may constitute part of a Trojan. However, sophisticated attackers can design Trojans that mimic normal circuit behavior, thereby evading such detection schemes. Functional analysis methods, including techniques like FANCI and VeriTrust, rely on simulation-based identification of nets with weak input-output dependencies or those not driven by legitimate functional inputs. Yet, these too have been shown to be circumventable through careful Trojan design that maintains plausible functional characteristics.

Symbolic algebra-based detection requires a golden reference model for comparison, which is typically unavailable when dealing with black-box 3PIP cores. Formal verification techniques, such as those using bounded model checking (BMC), attempt to mathematically prove the absence of information leakage or unauthorized data modification. While theoretically sound, these methods suffer from inherent scalability limitations due to the state-space explosion problem; they can only verify behavior up to a bounded number of clock cycles, allowing Trojans with deep sequential triggers—such as those incorporating counters or finite state machines (FSMs) with long activation sequences—to remain undetected. Similarly, commercial tools like JasperGold Security Path Verification leverage formal methods to check for information flow between designated secure assets and potential leakage points, but their effectiveness depends critically on the designer’s ability to correctly identify all relevant internal signals—a task that is infeasible under black-box assumptions.

Information flow tracking (IFT) techniques, including gate-level IFT (GLIFT), associate taint tags with sensitive data and monitor their propagation through the circuit. Although GLIFT provides fine-grained visibility into actual data flows, it is susceptible to “taint explosion” in designs with scan chains (common in DfT-inserted netlists), where a single tainted bit can contaminate an entire scan chain, rendering the analysis meaningless. Furthermore, GLIFT cannot distinguish between legitimate and malicious data paths if both terminate at the same authorized output port, leading to false negatives for Type I Trojans that exploit valid interfaces for covert leakage. Proof-carrying code (PCC) and sensitivity tracing approaches assign numerical sensitivity values to signals based on their proximity to secrets, but attackers can design bypass paths that avoid altering these values, thereby evading detection. Collectively, these limitations underscore the urgent need for a robust, reference-free, and comprehensive Trojan detection framework capable of operating under realistic black-box conditions and overcoming the evasion tactics employed by modern hardware adversaries.

## DETAILED DESCRIPTION

The present invention discloses an information flow security (IFS) verification framework specifically engineered for the detection of hardware Trojans in third-party intellectual property (3PIP) cores within system-on-chip (SoC) designs. This framework operates without requiring a golden reference model and is applicable to synthesized gate-level netlists, including those augmented with design-for-test (DfT) structures such as scan chains. The core innovation lies in modeling sensitive assets—such as cryptographic keys, privilege tokens, or confidential data—as stuck-at-0 and stuck-at-1 faults and leveraging automatic test pattern generation (ATPG) algorithms to detect the propagation or activation of these faults, thereby revealing violations of predefined confidentiality and integrity policies.

The SoC design flow, as contemplated by the invention, involves an SoC integrator who specifies system requirements and procures necessary IP cores either in-house or from external 3PIP vendors. Trusted entities include the SoC integrator and internal CAD tools, while all 3PIP vendors—including those supplying soft (RTL), firm (gate-level), or hard (GDSII) IP—and third-party DfT insertion services are considered untrusted. The threat model assumes adversaries may implant hardware Trojans comprising a trigger circuit that monitors rare events and a payload that executes malicious actions upon activation. The invention focuses on two primary Trojan categories: Type I Trojans, which leak assets through authorized output ports via bypass paths, and Type II Trojans, which exfiltrate data through functionally isolated, unauthorized leakage circuits.

The detection framework, embodied as software executable on a computing device comprising a processor circuit and memory, initiates by receiving a gate-level netlist of the 3PIP core, a technology library, and definitions of critical assets. The framework first enhances observability and controllability by dynamically enabling partial-scan capabilities on all flip-flops using ATPG tool features such as Tetramax’s “What If” analysis, without requiring physical resynthesis. For confidentiality verification, each asset is modeled as a dual stuck-at fault, and sequential ATPG is employed to identify all observe points—primary outputs or scan flip-flops—through which the asset’s logical value can be inferred. The algorithm iteratively propagates the fault through successive levels of sequential elements by selectively masking and unmasking flip-flops, thereby constructing complete asset propagation paths along with the required stimulus vectors.

Malicious observe points are then distinguished from legitimate ones using two complementary techniques. For Type I Trojans, the propagation depth—the number of logic gates traversed—is analyzed; bypass paths exhibit significantly shorter depths than valid cryptographic data paths, and synthesis optimization ensures redundant logic cannot mask this discrepancy. For Type II Trojans, an intersect analysis compares the fan-in cones of identified observe points against those of authorized outputs (e.g., ciphertext ports in an AES module); any observe point outside the authorized cone indicates a policy violation. Similarly, integrity verification identifies control points—primary inputs or scan flip-flops—that can influence an asset’s value. Malicious control points are flagged using analogous depth and intersect analyses relative to authorized control sources.

The framework further extracts Trojan triggering conditions. Simple triggers are directly inferred from stimulus vectors. For FSM-based triggers, the invention identifies state registers via feedback loops, then applies FSM extraction to reconstruct the state transition graph and derive the input sequence that activates the payload. This method is unbounded by clock cycle limits, overcoming a critical weakness of formal verification.

The computing device executing the framework includes volatile and nonvolatile memory storing HDL-derived netlists, ATPG engines, and custom scripts. The framework may be implemented purely in software, in dedicated hardware, or as a computer-readable medium. Variations include alternative ATPG tools, different asset definitions, and integration into existing EDA flows. The scope encompasses all embodiments that model assets as faults and use ATPG for IFS policy enforcement, irrespective of specific implementation details, thereby providing a robust, scalable, and evasion-resistant solution to the 3PIP trust problem.
