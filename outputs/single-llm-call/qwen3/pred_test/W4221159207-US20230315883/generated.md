## BACKGROUND

Entity resolution is a computational process by which records from disparate datasets are identified as referring to the same real-world entity, despite variations in data representation, formatting, or entry errors. This task is critical in domains such as healthcare, finance, and law enforcement, where accurate linkage of patient records, customer identities, or criminal histories across institutions enables improved decision-making, regulatory compliance, and operational efficiency. However, the sensitive nature of the underlying data—such as names, addresses, social identifiers, or medical histories—often prevents direct sharing between organizations due to legal, ethical, or privacy constraints. Traditional approaches to entity resolution rely on centralized data aggregation or deterministic matching on unique identifiers, both of which are infeasible in environments governed by data protection regulations such as HIPAA, GDPR, or CCPA. As a result, there exists a pressing need for methods that enable accurate record linkage while preserving the confidentiality of the source data. Private set intersection is a cryptographic technique that allows two parties to compute the exact overlap of their respective datasets without revealing any additional information beyond the size of the intersection and the identities of the matching elements. While effective for exact matches, such as comparing social security numbers or encrypted identifiers, private set intersection fails to accommodate the real-world variability inherent in textual fields such as names, addresses, or phone numbers, where typographical errors, abbreviations, or formatting differences render exact matches rare. Local sensitivity hashing, in contrast, is a probabilistic technique designed to map similar inputs to the same or closely related hash values, thereby enabling approximate matching. Unlike cryptographic hash functions, which are designed to minimize collisions, locality-sensitive hashing deliberately promotes collisions for semantically similar inputs, making it well-suited for fuzzy matching tasks. However, when applied naively, the output of locality-sensitive hashing can expose patterns or distributions of the underlying data, enabling inference attacks or brute-force reconstruction of sensitive records. The convergence of these two techniques—private set intersection for secure comparison and locality-sensitive hashing for approximate matching—has remained an unsolved challenge in privacy-preserving data linkage, primarily due to the difficulty of maintaining both accuracy and privacy in a scalable, linear-time protocol without reliance on trusted third parties.

## SUMMARY

A novel method for private data intersection is disclosed, wherein two or more parties each holding a private dataset of records perform a secure and efficient linkage of similar records without revealing the content of non-matching records. The method begins by preprocessing each record to normalize and canonicalize its fields, followed by the generation of shingles from the normalized text fields, where each shingle represents a contiguous substring of a specified length. Min-hash values are computed for each shingle using a family of collision-resistant hash functions, and these min-hash values are grouped into bands, each consisting of a fixed number of consecutive min-hash values. Each band is then hashed to produce a band signature, resulting in a compact representation of the record that preserves its similarity characteristics. The band signatures of all records from each party are collected into an ordered list and encrypted using a private key derived from a Diffie-Hellman key exchange protocol, ensuring that the raw signatures remain cryptographically protected. The encrypted band signatures are exchanged between the parties, and a private set intersection protocol is jointly executed to determine which encrypted signatures are common to both datasets. Upon identifying intersecting encrypted signatures, each party maps these back to the original record identifiers to determine which records are similar. To enhance privacy and prevent inference of missing records, a secret permutation is applied to the ordered list of encrypted signatures prior to exchange, ensuring that the positional relationship between records is obscured. A computer program product is provided, comprising a non-transitory computer-readable storage medium storing program instructions that, when executed by a processor, cause the processor to perform the steps of preprocessing records, computing min-hash values, grouping them into bands, generating band signatures, applying private set intersection, and determining matching records. The computer system includes a server configured to execute the private data intersection program, with components including a memory for storing datasets and program instructions, a processor for executing cryptographic operations and hash computations, and a network interface for secure communication with remote computing devices. The program instructions are executable in various forms, including assembler instructions, instruction set architecture instructions, and machine-level instructions, and may be stored on removable media, downloaded over a network, or embedded in electronic circuitry for dedicated hardware execution. The system supports deployment in cloud computing environments, wherein multiple clustered servers provide scalable resources for processing large-scale datasets across distributed nodes, with communication secured via TLS 1.3 and mutual authentication protocols.

## DETAILED DESCRIPTION

Entity resolution and private set intersection are foundational components of modern data linkage systems, particularly in contexts where sensitive information must remain confidential. Entity resolution seeks to identify matching records across datasets despite variations in data representation, while private set intersection ensures that only the intersection of sets is revealed, preserving the privacy of non-matching entries. Existing protocols for private record linkage often suffer from inefficiencies, high computational overhead, or insufficient privacy guarantees. Many rely on third-party intermediaries, which introduce trust assumptions and single points of failure. Others employ homomorphic encryption or garbled circuits, which, while secure, incur prohibitive computational costs that render them impractical for datasets exceeding tens of thousands of records. Furthermore, methods based on Bloom filters or locality-preserving hashes are vulnerable to reconstruction attacks due to their data-dependent nature and lack of formal security analysis. The present invention overcomes these limitations by introducing a novel protocol that integrates locality-sensitive hashing with private set intersection in a manner that is both computationally efficient and provably secure against semi-honest adversaries. The core innovation lies in the application of locality-sensitive hashing to generate band signatures from record fields, followed by the use of a private set intersection protocol to compare these signatures without exposing their underlying content. The locality-sensitive hash function employed herein is based on the Jaccard similarity coefficient, which measures the overlap between sets of k-shingles extracted from normalized text fields. Each record is transformed into a set of overlapping substrings of fixed length, and min-hash values are computed for each shingle using multiple independent hash functions. These min-hash values are partitioned into B bands, each containing R consecutive min-hash values, and each band is hashed independently to produce a single signature. The resulting tuple of band signatures constitutes the locality-sensitive hash of the record. The use of band signatures enables a probabilistic match declaration: two records are deemed similar if they share at least one identical band signature. This approach reduces the complexity of pairwise comparison from O(n²) to O(n), making large-scale linkage feasible. The private set intersection protocol is implemented using a Diffie-Hellman-based construction, wherein each party encrypts its band signatures using its private key and exchanges the encrypted values with the other party. The receiving party further encrypts the received values using its own private key and returns them, enabling the sender to compute the intersection by decrypting only those values that were doubly encrypted. To prevent the inference of missing records, a secret permutation is applied to the ordered list of encrypted signatures before transmission, ensuring that the mapping between record position and signature remains hidden. The system further incorporates optimization techniques to improve accuracy and performance, including the adjustment of B and R parameters to control the trade-off between false-positive and false-negative rates. Analytical formulas are derived to determine optimal values of B and R for a desired Jaccard similarity threshold, and empirical search methods are employed to fine-tune these parameters for specific datasets. The Jaccard similarity index is computed as the ratio of the size of the intersection of shingle sets to the size of their union, and its estimation from band matches is supported through binomial confidence intervals. The system supports weighted shingles, wherein certain fields (e.g., name or date of birth) are assigned higher importance by adjusting the frequency of their shingles in the min-hash computation, achieved through a novel hash-dropping transformation that mimics shingle duplication without increasing computational load. The private data intersection program is implemented as a modular software component executable on a server, which communicates with user devices via a secure network interface. The server includes a data processing engine, a cryptographic module, a memory subsystem for storing datasets and intermediate results, and a configuration manager for defining field weights, shingle lengths, and band parameters. The system supports deployment in cloud computing environments, with service models including infrastructure-as-a-service, platform-as-a-service, and software-as-a-service, and deployment models encompassing public, private, hybrid, and community clouds. The computer-readable storage medium may include volatile and non-volatile memory, removable media such as USB drives or optical discs, or firmware embedded in dedicated hardware. Program instructions may be downloaded over a network, stored locally, or executed directly from a remote server. The system architecture includes a functional abstraction model with layers for data input, preprocessing, hashing, private intersection, matching, and output, each layer interacting through well-defined interfaces. The user device provides a graphical user interface for initiating linkage requests, viewing results, and configuring privacy parameters, while the server executes the private data intersection program in a secure execution environment. The method is further enhanced by the introduction of a revealing variant, wherein parties may optionally compute the precise Jaccard index for matched records through a secondary private set intersection over the shingle sets, without revealing the full content of the records. This enables post-hoc validation of matches while preserving the confidentiality of non-matching data. The system supports multi-party configurations, wherein three or more entities may participate in a joint linkage protocol through sequential pairwise interactions or through a distributed coordination mechanism.
